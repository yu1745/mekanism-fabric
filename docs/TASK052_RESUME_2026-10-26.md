### Recipe serializers: one catalog, not two

`FabricRecipeRegistration` carried a hand-written copy of the 26 official serializers and deliberately skipped the four specials, so every `mekanism:mek_data` document failed with `Unknown registry key ... mekanism:mek_data` and 85 recipes were dropped. The duplicated list is gone; the platform now commits the official `MekanismRecipeSerializersInternal`:

- Ported to `MekanismDeferredRegister<RecipeSerializer<?>>` with `MekanismAPI.MEKANISM_MODID`; the official static block's assignments into `MekanismRecipeSerializers.*` are dropped because those api fields are keyed holders that resolve from the registry by id.
- The four specials are declared as typed holders and registered: `mek_data` (recipe-upgrade shaped recipe), `clear_configuration`, `bin_insert`, `bin_extract`.
- Recipe-upgrade data adapted to the platform: `FluidRecipeData` uses `mekanism.api.fluid.FluidStack`; `RecipeUpgradeData` uses `mekanism.api.INBTSerializable` (the NeoForge interface the official code bounds on); `ItemRecipeData` replaces NeoForge's `ItemHandlerHelper.insertItemStacked` with the same two-pass Mekanism-slot insertion (matching stacks, then empty slots) over `IInventorySlot#insertItem`. `ItemStack#isComponentsPatchEmpty()` (NeoForge addition) becomes `!getComponentsPatch().isEmpty()`.
- NeoForge's `PlayerEvent.ItemCraftedEvent` has no Fabric counterpart. `BinInsertRecipe#onCrafting` now takes `(ItemStack result, Container craftingMatrix)`, and the platform `ResultSlotCraftingMixin` injects the call at the same point NeoForge fires the event: after `ItemStack#onCraftedBy` in `ResultSlot#checkTakeAchievements`, before the crafting matrix is drained. It is registered in `mekanism.mixins.json` and admitted to the platform slice.

## Play-phase client→server channel — the 25 official C2S payloads are live

The server could send every official play payload but accepted none: the whole `mekanism.common.network.to_server` package was outside the slice, so no GUI action (side configuration, ejection, filters, frequency, security, module settings, mode/key, dropper, portable teleporter, robit name/skin) could reach a machine. The package is now ported and registered.

### Port shape

- `IMekanismPacket` already defines `handle(Player)`; the 25 packets now use it, with `Player` imports added where the parameter only existed through NeoForge's context. `PacketUtils.config/ejector/filterManager/blockEntity(player, pos)` call sites pass the resolved player.
- Ids use `ResourceLocation.fromNamespaceAndPath("mekanism", ...)`; the excluded entrypoint's `Mekanism.rl`, `Mekanism.keyMap` and `Mekanism.logger` map to the resource id factory, `KeySync.INSTANCE` and `MekanismAPI.logger`.
- `PacketModeChangeCurios` is deliberately **not** ported: Curios is a NeoForge/Forge mod with no Fabric counterpart, and its handler calls `CuriosIntegration`. The official `PacketModeChange` (equipment slots) remains.
- `PacketUpdateModuleSettings` invalid-config rejection: NeoForge's `IPayloadContext#disconnect` becomes `ServerPlayer#connection#disconnect`, since a play payload has no context-owned disconnect on Fabric.
- `PacketDropperUse` resolves the held dropper's tank through `ContainerType.FLUID.createHandler(stack)` (the attachment-backed owner) instead of the Forge item fluid capability; foreign fluid-item capabilities have no attachment-backed equivalent (documented delta).
- `PacketPortableTeleporterTeleport` posts the real `MekanismTeleportEvent.PortableTeleporter` through the port's `MekanismEventBus` (same cancellation contract as the NeoForge bus) and uses the resource id factory for its payload type.
- `AbstractContainerMenu#synchronizeCarriedToRemote` is private in vanilla but used to resync the gauge dropper's carried stack; it is added to `mekanism.accesswidener` (`accessible method ... synchronizeCarriedToRemote ()V`).

### Registration

`FabricServerPlayNetworking` registers all 25 types in `PayloadTypeRegistry.playC2S()` and one `ServerPlayNetworking` receiver per type that dispatches `payload.handle(context.player())`; a duplicate receiver fails loudly instead of silently dropping. It is common-safe, so an integrated server accepts the same payloads, and it logs `MEKANISM_FABRIC_SERVER_PLAY_PROOF payloads=25 direction=C2S`.

### Verified

- `./gradlew -p fabric compileJava --rerun` PASS (12 initial errors: missing `Player` imports, leftover `context` arguments, duplicate `player` locals, private `synchronizeCarriedToRemote`).
- `./fabric-build.sh remapJar` PASS (release build + five Knot runtimes + test contract).
- Clean packaged dedicated server: `MEKANISM_FABRIC_SERVER_PLAY_PROOF payloads=25`, `recipe_types=26 serializers=30`, `Loaded 2548 recipes`, zero `Parsing error`, `Done (6.6s)`; log at `/tmp/mek-smoke.RSjBnC/server.log`.

**Not verified:** no client sends these payloads yet (the client GUI/render lane is unported), so handler bodies are compile- and registration-verified but not exercised by a real click. `PacketModeChangeCurios` stays unported pending a Curios equivalent.

## First real machine run — a runtime-only remap defect fixed, and a durable end-to-end gate

Registration and recipe loading did not prove that a machine could tick. Placing an enrichment chamber in a packaged server and injecting energy/input through `data merge block` surfaced a crash that no compile or startup gate could see:

```
java.lang.AbstractMethodError: Receiver class mekanism.common.tile.machine.TileEntityEnrichmentChamber does not define or inherit
an implementation of the resolved method 'net.minecraft.class_1937 getLevel()' of interface IRecipeLookupHandler
    at RecipeCacheLookupMonitor.validatedBinding(...)
```

### Root cause

`IRecipeLookupHandler` declared `Level getLevel()` abstract so handlers could expose their world. In development names this is satisfied by the inherited `BlockEntity#getLevel`, but after remapping the vanilla method becomes `method_10997` while the mod interface keeps `getLevel` (the interface is not in a Minecraft supertype chain, so override propagation never reaches it). Every block entity therefore had an unimplemented abstract interface method, and the first recipe-machine tick crashed the server. This affects any mod interface that redeclares a mapped vanilla method name, so it was audited rather than patched at one call site:

- `IRecipeLookupHandler.getLevel`, `ITileWrapper.getLevel/getBlockPos` and `IQIOCraftingWindowHolder.getLevel` were the only three hits in the admitted sources whose implementers inherit the vanilla method.
- They now share one `mekanism.common.base.ILevelProvider` default that delegates to `BlockEntity#getLevel()`. Each contract extends it, so exactly one default exists (two unrelated defaults for one signature do not resolve, and abstract-plus-default is rejected by javac once the dependent class is really recompiled). Plain implementers keep their explicit overrides: `Transmitter` for the wrapper, `PortableQIODashboardInventory` for the QIO holder.
- `ITileWrapper#getBlockPos` stays a default for the same reason; it is only used by block-entity tiles (the transmitter overrides it).

**Methodology note:** the incremental build had hidden the compile-time consequences of the first attempt; `./gradlew -p fabric compileJava --rerun` must follow any interface-hierarchy change, just as it must for ordinary error counting.

It places an enrichment chamber and an energized smelter, writes energy and two iron ore into them with `data merge block`, also places a universal cable and a QIO dashboard, waits 20 s, and asserts the serialized state contains `mekanism:dust_iron` (2 ore → 4 dust) and `minecraft:iron_ingot`, with no parse error, no uncaught exception and no crash report. The QIO dashboard and the transmitter tick without error, which exercises the QIO holder/level and transmitter wrapper paths.

**Evidence:** `./gradlew -p fabric compileJava --rerun` PASS, `./fabric-build.sh remapJar` PASS, slice gates PASS, `scripts/fabric-machine-smoke.sh` PASS (7/7 checks; log `/tmp/mekanism-machine-smoke.xRJWnB/server.log`). ## Energy network vertical — four runtime defects between a placed cube and a running machine

The direct-energy machine test proved the recipe/energy math, but the real gameplay path (storage → cable → machine) was dead. Driving it exposed four separate defects, each invisible to compilation and to a bare startup:

1. **`ForgeEnergyCompat.capabilityExists()` asked for the wrong mod id** (`teamreborn` instead of `team_reborn_energy`). No energy compat was considered loaded, so the acceptor caches were built empty and the compat API reported unusable.
2. **Capability exposure never opened for a runtime-placed tile.** `FabricCapabilityTileLifecycle` opens exposure on `ServerBlockEntityEvents.BLOCK_ENTITY_LOAD`, which Fabric fires for chunk-loaded block entities; a machine placed by a player (or by `/setblock`) is attached through `LevelChunk#setBlockEntity` and never fires it. Every provider returned `null` until the chunk reloaded, so no cable could connect to a newly placed machine. `CapabilityTileEntity#setLevel` now opens exposure when the tile enters a `ServerLevel` (and unload/removal still close it).
3. **The Fabric energy acceptor cache was double-wrapped.** `BlockEnergyCapabilityCache#getCapability()` already returns a `IStrictEnergyHandler` on this port, but `EnergyAcceptorCache` still fed that value to `IEnergyCompat#wrapAsStrictEnergyHandler`, casting the handler to `EnergyStorage` → `ClassCastException` inside the cable's first `refreshConnections`. It now returns the cached handler directly.
4. **The universal cable exposed no energy capability.** The official `registerCable` called `EnergyCompatUtils.addBlockCapabilities(builder)`; that helper was replaced by the Fabric exposure seam and the call site lost the provider. Cables could therefore never accept energy from a cube, generator or another cable; `registerCable` now attaches `CapabilityTileEntity::basicCapabilityProvider` for `EnergyStorage.SIDED`.

The block-item side config is not a defect: a machine's default energy/input sides come from `AttachedSideConfig` on the **item**, applied by vanilla block placement. The smoke applies the equal side config through `data merge block` (`config0` = energy, `DataTypes` all INPUT, `eject0` = auto-eject for the source cube) because `/setblock` places no item components.

### Verified

The committed `scripts/fabric-machine-smoke.sh` now drives both paths in one server and passes 9/9:

- direct energy: 2 iron ore → 4 iron dust; 2 iron ore → 2 iron ingots;
- cable network: cube (100,000 J, auto-eject, all sides output) → basic universal cable → chamber (all sides energy input). The chamber reaches 19,950 J while processing and produces 2 dust from 1 of 2 ore, the cable carries 8,000 J, and the cube falls to 52,150 J;
- no parse error, no uncaught exception, no crash report, `MEKANISM_FABRIC_SERVER_PLAY_PROOF payloads=25`.

**Evidence:** `./gradlew -p fabric compileJava --rerun` PASS, `./fabric-build.sh remapJar` PASS, slice gates PASS, `scripts/fabric-machine-smoke.sh` PASS (log `/tmp/mekanism-machine-smoke.aA3ksO/server.log`). Intermediate crash report for the double-wrap: `/tmp/mek-enet6.qP62Ae/crash-reports`.

**Remaining boundaries:** a vanilla hopper cannot insert into a Mekanism machine on Fabric (vanilla uses `Container`; machines expose `ItemStorage.SIDED`), and item/fluid/chemical transport networks were not exercised yet. Client GUI configuration packets and rendering are still unported, so side config and eject toggles are only proven through NBT/state, not through the GUI.

## Machine auto-ejection probe (item verified, chemical unconfirmed)

A short probe checked whether a machine pushes its own output into an adjacent inventory when the relevant transmission side is configured as output and ejection is enabled (the item/fluid/chemical transmission types use `config<ordinal>` + `eject<ordinal>`, with `RelativeSide` order FRONT/LEFT/RIGHT/BACK/TOP/BOTTOM and `facing=north` mapping east→LEFT):

- **Items: pass.** Enrichment chamber (2 ore, 20,000 J, item output on LEFT, `eject3`) delivered 2 iron dust to an adjacent chest while retaining 2 in its output slot.
- **Chemicals: not confirmed.** Electrolytic separator (2,000 mB water, 200,000 J, chemical output on LEFT, `eject2`) produced 800 hydrogen + 400 oxygen in its internal tanks but delivered nothing to an adjacent `basic_chemical_tank` whose chemical input was enabled on all sides. The destination tank also stayed empty across repeated runs with enough energy, so this is a genuine open question in the chemical ejector path (`TileComponentEjector` chemical branch → `getChemicalCapabilityCaches`/`ChemicalUtil.emit`), not an energy or timing artifact. It is recorded as a gap, not fixed in this pass.
- **Fluids: not exercised** (no machine in the current set produces a fluid into an adjacent tank).

This probe is not part of the committed smoke gate; the item result is evidence that the ITEM ejector path works, and the chemical case is the next focused investigation if auto-ejection is prioritised.
