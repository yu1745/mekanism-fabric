## Ownership change, not a global flush emulation

The official base monitor reads `CommonWorldTickHandler.flushTagAndRecipeCaches`. That process-global one-tick flag is not the Fabric lifecycle owner; do not port the world tick handler or recreate the flag. Existing RecipeCacheContext binds on successful server/client publication, retains identity after failed reload, and clears on stop/disconnect. Monitors must use that same context.

- Retain the official public/protected monitor surface and `ICachedRecipeHolder` lookup protocol: no-recipe memoization, contents callback then onChange/unpause, change notification before processing, saved operating ticks, constant chemical saved usage, wrong-cache-index behavior, and energy-delta reporting. Factory onChange must continue to request sorting; its explicit updateCachedRecipe must retain its selected recipe and not spuriously load saved state or discard that selection on the next tick.
- Observe an opaque binding publication identity and an explicit cache-invalidation generation/token. Avoid retaining an entire old Binding/manager/access graph solely for identity tracking. Rebinding even to the same manager/epoch is a fresh identity; another manager/thread must not reuse an old CachedRecipe or no-recipe memo.
- Explicit `MekanismRecipeType.clearCache()` currently discards lists/indices without replacing the binding. Extend the existing binding with a narrowly scoped invalidation generation/token and advance it once per full owner clear, so monitors cannot keep processing a cached recipe after an explicit clear. Preserve the meaning of epoch and the existing publication identity (a clear is not a successful datapack reload). Do not introduce another ThreadLocal or a global counter. Individual index clears need not pretend a new datapack publication occurred.
- `invalidateCache()` is a predicate, not an acknowledgement: calling it before update must not consume invalidation and allow stale processing. Acknowledge the observed stamp only after a successful cache-resolution/update path; failures must not mark stale state current. Use the existing ICachedRecipeHolder protocol rather than rewrite its algorithm for a special machine.
- With no published context, monitors must not process an old cached recipe; detach its references and deliver the normal changed-to-null notification once through updateAndProcess. A real non-null handler Level with a manager differing from the bound manager must fail before stale cache processing, even if `CachedRecipe.isInputValid()` is still true and would otherwise bypass recipe lookup.
- Check explicit Factory.updateCachedRecipe as a second state-write entry point: it must participate in the same binding/invalidation ownership contract, not keep an untracked stale cache. Preserve its official callback and saved-state semantics.
- Handler interface default methods continue forwarding through the real canonical provider/cache with correct direction and input order. Do not duplicate the existing index matching matrices.

Implementation details may follow the smallest coherent design inside this boundary. If correct monitor ownership requires losing an official public method, using fake/no-op production types, or changing an unrelated machine lifecycle, report the exact blocker and parent decision needed before expanding.
