## Actual ownership, not a fluid analogy

- Full reads: `HandlerTransitRequest.java`, `TransporterManager.java`, `CursedTransporterItemHandler.java`. Prior parent full TransitRequest read recorded in REVIEW_06. Excerpts read: LogisticalTransporterBase 140–305 and 440–528; TransporterStack 155–274; TransporterPathfinder 110–174; TileEntityLogisticalSorter 110–174,263–322; TileComponentEjector 267–355.
- HandlerTransitRequest groups HashedItem by real integer source slots in insertion order. HandlerItemData.use executes source extractItem and then decrements predictions even on mismatch (logs only). It returns remaining item data, not extracted contents. This cannot simply become a Storage view-index facade: arbitrary Storage views have no stable indexed slots. Ejector rebinds the sided source handler across outputs but shares a request per DataType based on its documented same-slot-layout invariant.
- Ejector, sorter, and transporter pulling all invoke insertion first then response.useAll. Source consumption is outside the insertion call. TransitRequest.simple is used for an in-flight stack's final delivery; that caller uses response.getRejected to update the actual TransporterStack or removes it, and must NOT call unsupported SimpleItemData.use.
- LogisticalTransporterBase.insert is route-specific: physical from-side/canReceiveFrom and stack.canInsertToTransporterNN, then path selection. updateTransit(true) publishes a stack into transit, sends sync packet and marks save BEFORE caller source debit. These are nontransactional owners, unlike fluid tank content snapshots.
- Publication starts even earlier: TransporterStack.setPath(updateFlowing=true) mutates TransporterManager.flowingStacks. RecalculateRRPath(updateFlowing=false) is NOT enough for a side-effect-free dry-run: TransporterPathfinder.getNewRRPath always mutates outputter.setRoundRobinTarget. A safe transactional transfer cannot just call existing insert(doEmit=false), debit source, then redo insertion with true and assume same route/no state change. Preserve selected path and arrange actual flowing/transit/RR/publication ownership explicitly.
- TransporterManager prediction is cumulative across actual and additional in-flight sets keyed by GlobalPos. It simulates each in-flight stack before candidates. Fully rejected flight on a different target face is ignored; partial rejection or same-face rejection blocks the candidate. Existing InventoryInfo caches slot contents/limits and synthesizes updates. Fabric equivalent needs cumulative abortable transaction state, not independent isolated simulations that forget earlier reservations; no invented slot limits or loss of side exception behavior. This is a platform delta to adjudicate, not a reason to delete prediction.
- CursedTransporterItemHandler's nine fake slots, per-tick reference-identity dedupe, and simulatedFlowingStacks belong to its NeoForge compatibility surface, NOT an approved Fabric model. Its useful domain identity is actual transporter + physical source position. Do not wrap it in a reverse Storage facade or preserve fake slots as the new internal architecture.
- Sorter delegates special transport to insertMaybeRR (filter color/min); ordinary target insertion goes through request.addToInventoryUnchecked. sendHome forwards to physical back inventory with force=false specifically to prevent sorter daisy-chain recursion. Preserve that route and strict/color/min/RR semantics.
