## Concrete transaction design constraints confirmed

- Parent re-read complete TransitRequest, HandlerTransitRequest and TransporterManager. Ordinary target insertion can use one nested transaction per candidate, enforce min on actual accepted count, and merge only accepted candidate into caller transaction. Prediction must retain cumulative successful in-flight inserts in one abort-only parent transaction; candidate checks nest inside it. Fully rejected different-face flight is ignored, partial rejection or same-face rejection rejects route. No simulated insertion is committed to real world.
- `LogisticalTransporterBase:176–303` final delivery mutates stack.itemStack, flowing membership, then local deletes set and later batch packet/map deletion. Atomic target delivery must snapshot the actual stack contents and flowing membership before decrement/removal; close/commit before scheduling ordinary tick deletion. Do not structurally remove transit map entries during its fast iterator. Partial remainder remains real owner state and route recalculation happens after transaction closes. Never invoke SimpleItemData.use for this owner.
- Initial `updateTransit:490–504` owns nextId/transit and immediate packet/save. New flight must be present in transit AND flowing within the transaction, so nested operations observe capacity reservations. Abort must restore all mutations including nextId and RR. Packets/save are deferred until successful outer commit, not flight creation. Keep rollback participants stable per real owner (fresh participants per operation cannot safely compose nested repeated operations).
- RR setters in sorter:276 and QIOExporter:241 currently only assign rrTarget. Transactional snapshot/restore can use that exact real owner state without compensating external effects. Snapshot before pathfinder, not after it; no second route calculation.
- Existing FabricItemStorage snapshots physical stacks and validates execution/read-back. Its documentation explicitly admits immediate backing-slot dirty/listener/save effects are observable even on abort. Do not claim this item migration eliminates that accepted adapter limitation. No changes have been made to the adapter here.
