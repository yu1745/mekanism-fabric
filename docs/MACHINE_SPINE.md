## Parent reconnaissance for the capability boundary (not a Task048 decision)

Read sources: `tile/base/CapabilityTileEntity`, `capabilities/CapabilityCache`, `resolver/ICapabilityResolver`, `resolver/BasicSidedCapabilityResolver`, `resolver/manager/{ICapabilityHandlerManager,CapabilityHandlerManager,ItemHandlerManager,EnergyHandlerManager}`, `fabric/.../{item/FabricItemLookup,energy/FabricEnergyLookup}`. No implementation or compile proof yet.

Concrete obligations, rather than recursive file-count blockers:

- `CapabilityCache` dispatches by **identity** of the capability, tracks unique resolvers for global invalidation, consults a real `TileComponentConfig` for disabled sides, and supports lazy resolver registration. A Fabric port must use actual lookup identities/provider registration, not a new generic Forge compatibility registry.
- `BasicSidedCapabilityResolver` caches physical-side handlers and a null-side read-only handler. `CapabilityHandlerManager` checks current container visibility before resolving and keeps the actual holder. `ItemHandlerManager` currently assumes NeoForge `ISidedItemHandler extends IItemHandler`; Fabric's transaction Storage is not that domain supertype. This is a real type/transaction boundary requiring an explicit design, not import replacement.
- Existing `FabricItemLookup.expose(IMekanismInventory, side, holder)` creates an actual transaction view but registers no provider. Its documented owner obligation is to cache per physical side and permanently invalidate old views on removal, reload, facing/side-policy and topology changes. `FabricItemStorage.invalidate()` already exists and retained iterators share its invalidation state.
- Existing `FabricEnergyLookup.expose(IMekanismStrictEnergyHandler, side, holder, conversion)` uses physical sides only. `EnergyHandlerManager` instead handles a null-side read-only internal proxy and several external API identities. Domain/internal access and external Fabric exposure must not accidentally be conflated. No null-side external exposure should be introduced to mimic NeoForge.
- `FabricEnergyStorage` currently has topology-count failure checks but **no explicit lifetime invalidate method** (source inspection only). The lookup's documentation requires owner lifetime invalidation. Before any real block provider is admitted, retained view access after owner removal/replacement must be addressed and tested; merely dropping a map entry is not evidence that an already-held storage stopped accessing the removed owner. Transaction rollback must still restore captured pre-removal state rather than be disabled by an invalidation guard.
- `CapabilityTileEntity` clears internal caches **before** world capability invalidation and clears at setRemoved/clearRemoved; full invalidation also notifies bounding positions through AttributeHasBounding. `TileComponentConfig` triggers per-resource/side invalidation and change listeners. Fabric BlockApiCache invalidation/neighbor callbacks and actual holder generation must be examined before deciding the adaptation. Patched BlockEntity setRemoved/clearRemoved invoke world invalidation in NeoForge; vanilla does not provide that same method contract.

Next planning must decide the real manager/provider/side-policy ownership together using the above sources and existing adapter tests. Do not rerun a repository-wide closure scanner, accept a fake TileComponentConfig, or admit a registry object after deleting its capability-provider registration. Task047 deliberately changes its base constructor to a vanilla holder so this later decision is not forced into a partial registry wrapper now.
